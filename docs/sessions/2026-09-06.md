# 2026-09-06 — Investigation: multi-day failure alerts

Trigger: Diego reported receiving failure alerts for several days.

## Source of the alerts

The alerts are `tools/watchdog.py` doing its job. The 6-hourly `Pipeline
watchdog` workflow found something failing on 20 of ~24 runs since 2026-09-01,
sent its SES alert each time, then exited 1 — so the watchdog also appears in
the failure list itself. The watchdog is the messenger, not the defect.

Evidence: run 34042591539 log, `NEEDS ATTENTION` block.

## Three independent defects behind the alerts

### 1. Release — Intel bottle leg breaks bottles for every platform

`bottle (macos-15-intel, sequoia)` fails at "Build bottle" on every release.
Homebrew has dropped macOS Intel x86_64 support (announced August 2025,
effective September 2026), so `pcre2` no longer publishes an Intel bottle and
`brew install --build-bottle` refuses:

    preston-check/tap/preston-check: The following formula cannot be installed
    from bottle and must be built from source.
      pcre2

The blast radius is much wider than one platform, because of job ordering in
`.github/workflows/release.yml`:

1. `update-tap-url` runs *before* the bottles and deliberately strips the
   `bottle do` block from the tap formula (release.yml:164-167), so installs
   fall back to source until fresh SHAs are written.
2. The `bottle` matrix runs. Four legs pass, the Intel leg fails. `fail-fast:
   false` lets the others finish, but the *job* still concludes `failure`.
3. `update-tap` declares `needs: [release, bottle]`, so it is **skipped** — the
   new bottle SHAs are never written back.

Net effect: the tap formula is left with no bottle block at all, so
`brew install preston-check` builds from source on every platform, including
the four that built bottles successfully. Verified identical on the last seven
releases (2026-09-04 → 2026-09-06): failed leg is only the Intel one, and
`update-tap` is `skipped` in all seven.

This is the highest-impact finding and it is a silent user-facing degradation —
the release is reported as failed, but nothing says "bottles were dropped".

### 2. Promotion-PR race — three phantom red runs per ingest cycle

`Tests`, `Lint community checks` and `Preston-Check Security Audit` fail on
`threat-intel/automerge-*` branches. The orchestrator opens the promotion PR
and merges it immediately; the merge deletes the branch out from under the
just-dispatched `pull_request` runs, which die with zero jobs and
`conclusion=failure`.

Confirmed by timing: run 34012744585 (Tests) created 2026-09-06T04:56:2x, PR
#876 `closedAt` 2026-09-06T04:56:30Z. All three runs report `jobs: []`.

Because a jobless run has no failed job to retry, the watchdog's
`rerun-failed-jobs` call answers HTTP 403 — the "re-run refused (HTTP 403)"
lines in the alert. These failures can never self-heal, so they sit in the
watchdog's lookback window and re-alert every cycle while new ones accumulate.

### 3. Watchdog cannot heal jobless runs

`rerun_failed()` only calls `rerun-failed-jobs`, which refuses runs that never
created a job — precisely the class defect 2 produces.

## Fix status

PR #861 (`fix/watchdog-promotion-pr-race`, opened 2026-09-01) already fixes
defects 2 and 3: it waits for the promotion PR's checks before merging, falls
back to the full `rerun` endpoint on 403, installs `bashlex` for the community
lint gate, and lints generated checks before they are committed.

It is `MERGEABLE` / `CLEAN` with all five checks green — and has sat unmerged
for five days. Written, never shipped. It does **not** address defect 1.

## Correction to an early reading

These failures are not new: `Tests` failures go back to 2026-05-03, `Release`
to 2026-05-28. What changed recently is alert volume, not the onset — the
watchdog now finds something failing on essentially every cycle.
